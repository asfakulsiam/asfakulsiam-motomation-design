# Variety test, 2026-10-11

Do different seeds produce structurally different designs? This file is the output of `node evals/variety.mjs` (defaults: category `ecommerce`, seeds 3101–3105, builds from `results/2026-10-11-benchmark-v2/`). Similarity is `scripts/lib.mjs` `similarity()` on structural fingerprints: 0 means nothing shared, 1 means the same fingerprint, and memory warns at 0.70 or more.

## Findings

- **Draws (Part A): 5 seeds gave 5 archetypes, 4 signatures and 4 mutations.** 1 of 10 pairs is at or above 0.70: seeds 3101 and 3104 share the `rows` layout family and a scroll signature, and their tiers differ by 3. Mean similarity is 0.28.
- **Builds (Part B): the 15 published skill builds use 12 different archetypes across 15 runs (timeline and room appear in both hotel and studio).** Within each brief, every signature is different. Within a brief, archetypes differ in 4 of 5 briefs. SaaS used `console` twice (2101, 2102), so **SaaS fails the release gate's variety rule** ("3 runs, 3 different archetypes and signatures") on archetype. The other four briefs pass it.
- **Max 1.00 in four briefs is a limit of the fingerprint, not identical pages.** A build's stamp gives only archetype, signature and tier. The builds' signatures are invented for each brief, not rows of `signatures.csv`, so their type is unknown. Every v2 build chose Tier 2. That leaves two dimensions, layout family and tier, so two different archetypes in the same family (timeline and room are both `sequence`) score 1.00. Measuring section order and type scale from the built HTML would make Part B sharper. That isn't done here.
- **Not done: 5 real builds of one brief.** That needs an agent run, and none was available in this environment (see `../README.md`, "Agents tested so far"). Part B uses the 3 builds per brief that already exist.

# v2.4.0 update: the SaaS `console` collision (fixed)

**Status: fixed in the generator and the rules; re-measured on real v3 builds in [`2026-10-11-benchmark-v3.md`](2026-10-11-benchmark-v3.md#variety-on-v3-builds).** The finding above is kept as it was published.

## Cause

Two causes, both found by reading the v2 transcripts and the runner:

1. **The evaluator's note reached the agent.** `evals/briefs/02-dev-tool-landing.md` ends with `**Expect:** … Console or Workbench thinking …`. The v2 runner sent the whole brief file to the generator, so every SaaS run (both arms) was told to think "Console". The same leak explains the v2 signature convergence on hotel ("a signature tied to doors" → three door signatures) and studio ("light" → two sun signatures).
2. **Overrides were hand-picked.** The engine drew `lookbook` (2101) and `gallery-wall` (2102). Both agents decided the draw didn't fit a SaaS page and replaced it with the first product-led archetype they knew. Hand-picked replacements converge.

## Fix

| Where | Change |
|---|---|
| `evals/run-agent-benchmark.mjs` | `generatorBrief()` strips the `**Expect:**` line from every generator prompt (baseline, gated, matched, skill). Judges still see it. |
| `scripts/collide.mjs` | Every draw now prints a **seeded fallback** ("If it can't serve the brief, take: …"): category-fit, never an archetype drawn in the run, preferring a different layout family. It uses its own seeded stream, so no existing draw changed (`--seed 42` output is identical apart from the new line). |
| `thinking/sequence.md` §3 | "When the draw doesn't fit": take the seeded fallback, not a favourite; anything else needs a one-line reason in the plan. |
| `thinking/sequence.md` §6 | **Controlled reuse** across separate projects (option b): an archetype may recur across projects or seeds only with a different mutation **and** a different fingerprint, written in the plan. Inside one project nothing is relaxed: memory blocks the repeat and the release gate still needs 3 different archetypes and signatures. |
