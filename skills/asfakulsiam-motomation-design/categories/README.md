# Categories

Each file is a **recipe** (authority level 7): the real job of that kind of site, starting dials, archetypes that can fit, one possible section order, optional treatments, conventions users expect, pitfalls, and a **Recipe contract** naming its intended context, assumptions, what it does not cover, required capabilities versus optional treatments, and when to reject or adapt it.

`portfolio` · `studio` · `ecommerce` · `saas` · `hotel` · `restaurant` · `organisation` · `event` · `architecture` · `personal-brand` · `product-launch` · `education`

**Order:** the project type and its scope come first (Step 1 in `thinking/sequence.md`: the product contract, type research and derived scope); a recipe is picked after, if one helps. Every recipe is optional design guidance: use it, adapt it, combine it with another, or ignore it. Not listed? Research the type as itself; do not force it into the nearest file. Combining two files is an option, never a requirement. A recipe's patterns are not a checklist to implement, and the concept may invent structures and interactions no recipe names, when the brief justifies them.

**A category file is design guidance, not scope.** Its section order or page set covers the pages it names. It is not the list of everything the site needs. The scope (routes, states, legal pages, admin surface, edge cases) comes from Step 1 in `thinking/sequence.md`, derived from research. If the derived scope and a category file disagree, the derived scope wins. This applies to every category.

**Twelve recipes cannot cover the web.** Marketplaces, B2B procurement, publications, dashboards, booking platforms, directories, communities and most real products have no file here, on purpose: they are researched as themselves (`craft/research.md`). A new recipe is added only when it adds value no research step would find, with a complete Recipe contract; a project's discovery does not automatically become a recipe.
